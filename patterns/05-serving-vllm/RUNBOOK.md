# RUNBOOK — vLLM на арендованном GPU (RunPod, 1×24 GB)

Рабочая шпаргалка: команды, что означает каждый флаг, как проверять, обо что спотыкается.
Заполняется по ходу прогона — раздел «Журнал падений» ведём в реальном времени, это главный
продукт этого файла.

Хост-машина: MacBook Pro M4 Max, 36 GB, CUDA нет → vLLM только на арендованном GPU.

---

## 1. Под

### Какую карту брать

Декодирование упирается в **пропускную способность памяти**, а не в вычислительную мощность:
на каждый токен веса модели прочитываются из VRAM целиком. Поэтому карту выбирают по
паре «сколько VRAM» + «сколько GB/s», а не по названию и не по TFLOPS. Второе требование —
архитектура **не ниже Ampere (sm80)**, иначе vLLM не сможет использовать ядра `awq_marlin`.

Модель `Qwen2.5-7B-Instruct-AWQ` — 5.5 GB весов, значит 24 GB достаточно с большим запасом
под KV-кэш. Всё, что выше, — переплата за память, которую нечем занять.

| Карта | VRAM | Пропускная способность | Архитектура | Цена/час | Вердикт |
|-------|------|------------------------|-------------|----------|---------|
| **RTX A5000** | 24 GB | ~768 GB/s | Ampere sm86 | **$0.27** | лучший выбор: дешевле всех 24 GB, marlin работает |
| RTX 3090 | 24 GB | ~936 GB/s | Ampere sm86 | $0.50 | запасной: быстрее по памяти, вдвое дороже |
| RTX 4090 | 24 GB | ~1008 GB/s | Ada sm89 | $0.74 | быстрейшая из 24 GB, но втрое дороже A5000 |
| L4 | 24 GB | ~300 GB/s | Ada sm89 | $0.49 | **не брать**: втрое меньше пропускная способность при цене выше A5000 |
| A40 | 48 GB | ~696 GB/s | Ampere sm86 | $0.44 | если нужен запас VRAM под модель побольше |
| H100 / A100 / B200 | 80–180 GB | 2–8 TB/s | Hopper+ | $1.39–6.79 | под 7B — деньги на ветер |

Порядок действий: **RTX A5000**, если недоступна (в списке «2 max») — **RTX 3090**, затем
**RTX 4090**. Обязательно **expose HTTP port 8000**, container disk 30 GB.

Стоимость считаем в минутах: A5000 ≈ **$0.0045/мин**, весь заход на 40–60 минут ≈ $0.20–0.30.
Правило сессии: не завелось за 15 минут — гасим под.

### Образ

`vllm/vllm-openai:latest` — vLLM уже установлен, ENTRYPOINT это сам API-сервер, поэтому в
поле **Container Start Command** идут только аргументы, без слов `vllm serve`. Не брать
голый `runpod/pytorch`: `pip install vllm` съест ~5 минут оплаченного времени.

## 2. Запуск сервера

Локально (или в терминале пода) это выглядит так:

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct-AWQ \
  --quantization awq \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.90 \
  --host 0.0.0.0 --port 8000
```

В **Container Start Command** на RunPod слова `vllm serve` не пишутся — они уже в ENTRYPOINT
образа. Проверяется это по дефолтной команде их шаблона: там имя модели стоит первым
**позиционным** аргументом (`Qwen/Qwen3-8B --host …`), а не через `--model`. Значит наша
строка:

```
Qwen/Qwen2.5-7B-Instruct-AWQ --quantization awq --max-model-len 8192 --gpu-memory-utilization 0.90 --host 0.0.0.0 --port 8000 --served-model-name qwen2.5-7b-awq --disable-log-requests
```

### Переменные окружения пода

| Переменная | Нужна? | Зачем |
|------------|--------|-------|
| `VLLM_API_KEY` | оставить | vLLM начинает требовать `Authorization: Bearer <key>`. URL `*.proxy.runpod.net` публичный — без ключа любой, кто знает POD_ID, тратит вашу карту. Значение `sk-$RUNPOD_POD_ID` подставляется RunPod'ом, то есть ключ выводится из ID пода |
| `HF_HOME` | оставить | куда качаются веса с Hugging Face. Если Volume disk = 0, это просто папка на container disk — веса не переживут перезапуск, что для одноразового пода нормально |
| `HF_TOKEN` | нет | нужен только для gated-моделей; Qwen2.5-7B-AWQ открытая |

### Флаги чужого шаблона, которые надо поменять

| Их дефолт | Наше значение | Почему |
|-----------|---------------|--------|
| `Qwen/Qwen3-8B` | `Qwen/Qwen2.5-7B-Instruct-AWQ` | сравниваем с тем же семейством, что гоняли в Ollama; AWQ — 5.5 GB весов вместо ~16 GB |
| `--enforce-eager` | **убрать** | отключает CUDA-графы: экономит немного памяти, но замедляет декодирование. Мы меряем скорость, и памяти на AWQ хватает — оставить его значит занизить собственный результат |
| `--gpu-memory-utilization 0.95` | `0.90` | 0.95 не оставляет запаса на фрагментацию: типичная причина OOM уже после успешного старта |
| `--max-model-len 8128` | `8192` | ровная степень двойки, совпадает с расчётом KV-кэша ниже |
| — | `--served-model-name qwen2.5-7b-awq` | короткое имя в API: одно и то же имя в curl, в бенче и в отчёте |

Что делает каждый флаг:

| Флаг | Что делает | Что будет, если ошибиться |
|------|-----------|---------------------------|
| `Qwen/Qwen2.5-7B-Instruct-AWQ` | HF repo id; веса тянутся при старте (~5.5 GB AWQ 4-bit vs ~15 GB fp16). Это же имя надо слать в поле `model` API-запроса | Скачивание ~2–4 мин — это оплаченное время пода |
| `--quantization awq` | Указывает формат квантованных весов. На Ampere+ (sm80+: A10 sm86, 4090 sm89, L4 sm89) vLLM сам подменит ядро на **awq_marlin** и напишет это в лог — оно быстрее. На sm75 (T4) marlin недоступен, останется медленный awq | Не указать → vLLM обычно прочитает `quantization_config` из config.json сам; указать неверный формат → падение на загрузке весов |
| `--max-model-len 8192` | Максимальная длина последовательности = верхняя граница KV-кэша на один запрос. Модель нативно умеет 32768 | Оставить 32768 → на старте `ValueError: ... KV cache ... Try increasing gpu_memory_utilization or decreasing max_model_len` |
| `--gpu-memory-utilization 0.90` | Доля VRAM, которую процесс забирает под **всё сразу**: веса + активации + KV-кэш. vLLM аллоцирует пул заранее, а не по мере роста | 0.95 → риск OOM от фрагментации/чужих процессов; 0.5 → мало блоков KV, низкая параллельность |
| `--host 0.0.0.0` | Слушать все интерфейсы. По умолчанию localhost — прокси RunPod не достучится | Молчащий порт снаружи при живом сервере внутри |
| `--port 8000` | Должен совпадать с exposed-портом пода | 502 от прокси |

Полезные добавки:

| Флаг | Зачем |
|------|-------|
| `--served-model-name qwen2.5-7b-awq` | Короткое имя в API — бенч дергает одно и то же имя на обеих базах |
| `--max-num-seqs 32` | Потолок одновременных секвенций в батче — прямой рычаг для теста конкурентности |
| `--disable-log-requests` | Лог каждого запроса замедляет сервер под нагрузкой и врёт в замерах |

### Арифметика KV-кэша (Qwen2.5-7B: 28 слоёв, 4 KV-головы GQA, head_dim 128, fp16)

```
KV на 1 токен = 2 (K и V) × 28 слоёв × 4 головы × 128 × 2 байта = 57 344 B ≈ 56 KiB
одна секвенция на 8192 токена ≈ 448 MiB
```

На 24 GB при `--gpu-memory-utilization 0.90`: 21.6 GB минус ~5.5 GB весов минус активации
→ ~15 GB под KV → **порядка 30 полных секвенций по 8k**.

Сверять не с этим расчётом, а с логом vLLM при старте: строка вида
`# GPU blocks: N, # CPU blocks: M` — умножить N на `block_size` (по умолчанию 16 токенов).
**Записать реальное N в журнал ниже** — это то число, которое называют на собеседовании.

## 3. Проверка (после старта, до бенча)

```bash
export POD=https://<POD_ID>-8000.proxy.runpod.net
export VLLM_API_KEY=sk-<POD_ID>
```

(Ключ — то, во что раскрылась `sk-$RUNPOD_POD_ID`; сверить можно в Environment пода.
Дальше он идёт в заголовке `Authorization: Bearer $VLLM_API_KEY`, а бенч читает его из
той же переменной — см. [harness/adapters.py](../../harness/adapters.py).)

Живой сервер и список моделей:

```bash
curl -s $POD/v1/models -H "Authorization: Bearer $VLLM_API_KEY" | python3 -m json.tool
```

Один запрос end-to-end (имя модели брать из ответа выше):

```bash
curl -s $POD/v1/chat/completions -H "Authorization: Bearer $VLLM_API_KEY" -H 'Content-Type: application/json' -d '{"model":"qwen2.5-7b-awq","messages":[{"role":"user","content":"Say OK"}],"max_tokens":16,"temperature":0}' | python3 -m json.tool
```

Проверка стрима (бенч меряет TTFT именно так):

```bash
curl -N -s $POD/v1/chat/completions -H "Authorization: Bearer $VLLM_API_KEY" -H 'Content-Type: application/json' -d '{"model":"qwen2.5-7b-awq","messages":[{"role":"user","content":"Count to 20"}],"max_tokens":64,"stream":true,"stream_options":{"include_usage":true}}'
```

Занятость KV-кэша и очередь под нагрузкой (Prometheus-метрики):

```bash
curl -s $POD/metrics -H "Authorization: Bearer $VLLM_API_KEY" | grep -E 'gpu_cache_usage|num_requests_(running|waiting)'
```

VRAM с самого пода:

```bash
nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv -l 5
```

## 5. Гашение пода

**Terminate, не Stop.** Stop продолжает тарифицировать диск.
После гашения — записать в журнал итоговое время работы пода в минутах и стоимость.

## Журнал падений (заполняется по факту)

| # | Симптом (точная строка из лога) | Причина | Чем починили | Мин. пода |
|---|--------------------------------|---------|--------------|-----------|
| 1 | `vllm: error: unrecognized arguments: --disable-log-requests`, следом `usage: vllm [-h] [-v] {chat,complete,serve,…}`, контейнер в рестарт-цикле | Флаг удалён в vLLM 0.26: логирование запросов теперь выключено по умолчанию, а включается обратным флагом `--enable-log-requests`. Совет из «общего знания» оказался про старую версию | Убрали флаг из Container Start Command | ~13 |
| 2 | Телеметрия: `Processes 0`, `VRAM 0%`, `Disk 106 MB` при зелёном `Ready` на порту 8000; curl отдаёт пустоту (`Expecting value: line 1 column 1`) | `Ready` у прокси RunPod означает «порт проброшен», а не «за ним кто-то слушает». Диагностировать надо по Telemetry + Logs, а не по индикатору порта | — (диагностический факт, а не поломка) | — |
| 3 | После **Edit Pod** сменился ID пода (`<old-id>` → `<new-id>`) | Правка Start Command пересоздаёт под, а не перезапускает контейнер. Старый URL и ключ `sk-<POD_ID>` мгновенно протухают | Взяли новый ID из списка подов, пересобрали `$POD` и `$VLLM_API_KEY` | ~2 |

Ожидаемые кандидаты, чтобы узнать в лицо:

- `ValueError: The model's max seq len (32768) is larger than the maximum number of tokens that can be stored in KV cache` → уменьшить `--max-model-len` или поднять `--gpu-memory-utilization`.
- `torch.OutOfMemoryError` на этапе профилирования → снизить `--gpu-memory-utilization` до 0.85; чужой процесс на GPU (`nvidia-smi`).
- В логе `Using awq_marlin kernel` вместо `awq` → это норма и это быстрее; отсутствие строки на 4090 — повод проверить версию vLLM.
- 502/таймаут от `*.proxy.runpod.net` при живом процессе → забыт `--host 0.0.0.0` или порт не exposed.
- Первый запрос в разы медленнее остальных → прогрев/CUDA-графы: в бенче нужен warmup-запрос вне статистики.

## Итоговые числа

Переносить сюда и в [README паттерна](README.md) только замеренное. Прочерк — честнее прикидки.

| Runtime | Модель | Конкурентность | TTFT p50/p95 | Decode tok/s на запрос | Aggregate tok/s | Wall |
|---------|--------|----------------|--------------|------------------------|-----------------|------|
| Ollama, `NUM_PARALLEL=1` | qwen2.5:7b Q4_K_M | c=1 | 0.11 / 0.12 с | 67.7 | 65.6 | 78.0 с |
| Ollama, `NUM_PARALLEL=1` | qwen2.5:7b Q4_K_M | c=20 | 37.61 / 69.76 с | 67.3 | 65.4 | 78.2 с |
| Ollama, `NUM_PARALLEL=8` | qwen2.5:7b Q4_K_M | c=20 | 25.66 / 50.04 с | 10.5 | 81.8 | 62.6 с |
| vLLM 0.26, RTX A5000 | Qwen2.5-7B-Instruct-AWQ | c=1 | 0.57 / 0.88 с | 125.5 | 95.8 | 53.4 с |
| vLLM 0.26, RTX A5000 | Qwen2.5-7B-Instruct-AWQ | c=20 | **0.60 / 0.99 с** | 87.0 | **1154.6** | **4.4 с** |

Замерено на Apple M4 Max 36 GB и на арендованной RTX A5000 (24 GB, EU-SE-1), 20 запросов ×
256 токенов, temperature 0, prefill ~126 токенов. KV-кэш при 8 слотах Ollama: 14336 MiB —
предсказание по формуле (32768 × 8 × 56 KiB) сошлось точно. У vLLM лог показал
`kv cache memory in use is 14.79 GiB` при 5.29 GiB весов — прикидка «~15 GB под KV, порядка
30 секвенций по 8k» подтвердилась (14.79 GiB / 56 KiB ≈ 277k токенов ≈ 34 секвенции).

**Оговорка про TTFT:** у vLLM в него входит round-trip до Швеции через Cloudflare (~0.4 с),
у Ollama — localhost. Сравнивать честно можно рост TTFT под нагрузкой, а не абсолют:
у Ollama 0.11 → 25.7 с (×230), у vLLM 0.57 → 0.60 с (×1.05).

### Итог одной строкой

Агрегированная пропускная способность: **81.8 → 1154.6 tok/s, ×14**. p95 TTFT: **50.0 → 0.99 с**.
Wall на тех же 20 запросах: **62.6 → 4.4 с**. Но главное не это, а поведение под нагрузкой:
скорость на пользователя при c=20 у vLLM просела на 31% (125.5 → 87.0), у llama.cpp — в 6.4
раза (67.3 → 10.5). Первое — continuous batching, второе — дележка одного потока между слотами.

Стоимость всего захода: ~25 минут пода RTX A5000 ≈ **$0.11** по тарифу сессии.

**Что уже видно без GPU:** поднятие лимита параллелизма с 1 до 8 дало +25% aggregate (65.4 → 81.8)
ценой падения скорости на пользователя в 6.4 раза (67.3 → 10.5 tok/s). Суммарная скорость сервера
на Metal — константа ~72–84 tok/s при любом размере батча (1 слот: 72.1, 4 слота: 4×20.6=82,
8 слотов: 8×10.5=84). Батч здесь делит одну скорость между пользователями, а не умножает её —
деквантование Q4_K на лету растёт линейно с батчем и съедает выигрыш от однократного чтения весов.
Именно это число и должен побить vLLM с ядрами Marlin.
